# MATCH 패턴의 화살표 방향이 뜻하는 것

## 문제의 쿼리

```gql
MATCH (s:Sensor)-[:monitors]->(m:Machine)-[:has_part]->(p:Part)<-[:inspects]-(qc:QualityCheck)
WHERE s.lastReading > s.threshold AND qc.passed = false
RETURN m.name, s.type, s.lastReading, p.name, qc.defectCode
```

이 한 줄은 "임계값을 넘긴 센서가 붙어 있는 기계 → 그 기계가 만든 부품 → 그 부품에서 불합격 판정이 난 검사" 를
한 번에 이어 붙인 **3-hop 경로 패턴**이다.

---

## 1. 화살표 문법 (ASCII-art pattern)

Cypher/GQL의 패턴은 그래프를 그림으로 그린 것에 가깝다. 노드는 괄호 `()`, 관계는 대괄호 `[]`,
그리고 그 사이를 잇는 선과 화살촉이 **간선의 방향**을 나타낸다.

| 문법 | 의미 |
|---|---|
| `(a)-[:REL]->(b)` | a 에서 b 로 향하는 `REL` 간선 (정방향) |
| `(a)<-[:REL]-(b)` | b 에서 a 로 향하는 `REL` 간선 (즉 패턴을 역방향으로 탐색) |
| `(a)-[:REL]-(b)` | 방향 무시. a→b 든 b→a 든 `REL` 이면 매칭 (무방향) |

화살표를 아예 빼면(`-[:REL]-`) 양방향 모두 매칭되므로 편해 보이지만,
방향 자체가 의미를 담고 있는 온톨로지에서는 잘못된 결과(예: 기계가 센서를 모니터링하는 경로)를 끌어올 수 있다.

## 2. 화살표는 "저장된 간선 방향"이지 "읽는 순서"가 아니다

가장 흔한 오해가 이 지점이다.

- **화살표 방향 = 온톨로지에 선언된 간선의 방향.**
  `monitors` 는 온톨로지에서 `Sensor → Machine` 으로 선언되었다. 그래프 안에 실제로 저장된 화살표가
  센서에서 기계 쪽을 향한다는 뜻이다. 이 방향은 쿼리를 어떻게 쓰든 바뀌지 않는 **데이터의 사실**이다.
- **패턴을 왼쪽에서 오른쪽으로 읽는 것 = 탐색(traversal) 순서.**
  이건 쿼리 작성자가 정하는 **서술 순서**일 뿐이며, 간선 방향과 아무 관련이 없다.

즉 패턴의 좌→우 진행 방향과 각 간선의 화살촉 방향은 **서로 독립적**이다.
그래서 좌→우로 쭉 읽어 나가면서도 어떤 hop 은 `->`, 어떤 hop 은 `<-` 가 섞여 나올 수 있다.
`<-` 가 나오면 "여기서는 저장된 화살표를 거슬러 올라간다"는 표시다.

동일한 경로를 아래처럼 순서를 통째로 뒤집어 써도 결과 집합은 같다.
(모든 화살촉이 함께 뒤집힌다는 점에 주목)

```gql
MATCH (qc:QualityCheck)-[:inspects]->(p:Part)<-[:has_part]-(m:Machine)<-[:monitors]-(s:Sensor)
```

## 3. hop 별 대응표

| hop | 패턴 조각 | 온톨로지 선언 | 패턴에서의 진행 방향 | 비고 |
|---|---|---|---|---|
| 1 | `(s:Sensor)-[:monitors]->(m:Machine)` | `monitors` — `Sensor` → `Machine` (many-to-one) | 정방향 (`->`) | 선언 방향과 읽는 방향이 일치 |
| 2 | `(m:Machine)-[:has_part]->(p:Part)` | `has_part` — `Machine` → `Part` (one-to-many) | 정방향 (`->`) | 선언 방향과 읽는 방향이 일치 |
| 3 | `(p:Part)<-[:inspects]-(qc:QualityCheck)` | `inspects` — `Quality-Check` → `Part` (many-to-one) | 역방향 (`<-`) | 부품에서 검사로 **거슬러 올라감** |

## 4. 왜 마지막 hop 만 뒤집히는가

패턴은 `Sensor → Machine → Part` 까지 자연스럽게 흘러와 `Part` 에 도착한 상태다.
그런데 온톨로지의 `inspects` 는 **`Quality-Check` → `Part`** 로 선언되어 있다.
검사가 부품을 검사하는 것이지, 부품이 검사를 "가리키는" 간선은 존재하지 않는다.

따라서 이미 손에 쥔 `Part` 에서 `QualityCheck` 로 도달하려면 방법은 하나뿐이다 —
**저장된 화살표를 거꾸로 타고 들어가는 것**. 그것이 `(p:Part)<-[:inspects]-(qc:QualityCheck)` 이다.

여기서 `-[:inspects]->` 라고 쓰면 "부품이 무언가를 검사한다"는, 온톨로지에 존재하지 않는 간선을 요구하는 셈이라
결과가 0건이 된다. 방향 오타는 에러가 아니라 **조용한 빈 결과**로 나타나기 때문에 특히 조심해야 한다.

이 역방향 hop 이 바로 아티클이 말하는 **피드백 루프**의 코드 표현이다.
생산 방향(`Machine → Part`)으로 흘러온 데이터에, 검사 방향(`Quality-Check → Part`)에서 들어온 정보를
`Part` 라는 공통 노드에서 만나게 하는 구조다. 두 화살표가 `Part` 를 향해 마주 보는
`Machine → Part ← Quality-Check` 모양이 그대로 패턴에 새겨져 있다.

## 5. 역방향 탐색의 비용

- **의미상 비용은 없다.** 속성 그래프에서 간선은 양쪽 끝 노드에서 모두 접근 가능하므로,
  역방향으로 탄다고 해서 결과가 달라지거나 부정확해지지 않는다. `<-` 는 순전히 "어느 쪽 끝에서
  출발하느냐"의 표기일 뿐이다.
- **다만 실행 성능은 다를 수 있다.** 엔진은 패턴 중 가장 선택적인(selective) 지점을 앵커로 잡고
  탐색을 시작하는데, 어느 방향에 인덱스가 걸려 있는지, 어느 쪽 카디널리티가 작은지에 따라
  실행 계획이 달라진다. 여기서는 `qc.passed = false` 와 `s.lastReading > s.threshold` 라는
  필터가 있으므로, 옵티마이저가 센서 쪽이 아니라 QualityCheck 쪽에서 시작해
  `inspects` 를 정방향으로 타고 내려오는 계획을 선택할 수도 있다.
- 요약: **방향 표기는 의미의 문제이고, 탐색 시작점 선택은 옵티마이저의 문제**다.
  작성자는 온톨로지 선언과 일치하도록 화살표를 정확히 쓰는 데 집중하면 된다.

---

## 한 줄 정리

화살표는 온톨로지에 선언된 간선의 방향을 그대로 그린 것이며, `->` 는 선언 방향대로,
`<-` 는 선언 방향을 거슬러 타고 들어감을 뜻한다. `monitors`(Sensor→Machine)와
`has_part`(Machine→Part)는 정방향이라 `->`, `inspects`(Quality-Check→Part)는
Part 에서 Quality-Check 로 도달해야 하므로 `<-` 로 뒤집혔다.

# Shopping-Cart의 `itemCount` / `subtotal`이 denormalized 속성인 이유

## 한 줄 요약

두 값 모두 **장바구니에 담긴 상품들(`contains` 관계)을 따라가면 계산해 낼 수 있는 값**인데,
계산하지 않고 **Cart 엔티티에 직접 저장해 두기** 때문에 비정규화(denormalized) 속성이다.
저장 공간과 정합성 관리 비용을 더 쓰는 대신, 질의 속도와 단순함을 얻는 트레이드오프다.

원문(`Shopping Carts` 아티클)의 표현:

> The `itemCount` and `subtotal` are denormalized summary properties — they could be computed from cart contents, but storing them directly makes queries faster.
>
> **Denormalized properties** (itemCount, subtotal) trade storage for query speed.

---

## 1. 해당 모델에서 무슨 일이 벌어지는가

Shopping-Cart 엔티티 정의:

| Property | Type | Identifier? |
|---|---|---|
| `cartId` | string | ✓ |
| `createdAt` | datetime | |
| `itemCount` | integer | |
| `subtotal` | decimal (USD) | |

그리고 관계:

- `contains` — `Shopping-Cart` → `Product` (many-to-many)
- `has_cart` — `Buyer` → `Shopping-Cart` (one-to-one)

즉 그래프상으로는 이미 "카트에 무엇이 들어 있는가"가 `contains` 간선으로 표현돼 있다.
그렇다면 원리적으로는:

- `itemCount` = `contains` 간선의 개수(수량을 고려하면 수량 합)
- `subtotal` = Σ (연결된 각 `Product.price` × 수량)

로 **언제든 유도(derive)할 수 있다**. 그런데도 굳이 별도 속성으로 들고 있으니, 이는 "사실을 한 곳에만 둔다"는
정규화 원칙에서 의도적으로 벗어난 설계다.

---

## 2. 정규화 vs 비정규화

| | 정규화(Normalization) | 비정규화(Denormalization) |
|---|---|---|
| 목표 | 중복 제거, 하나의 사실은 한 곳에만 | 조회 성능, 질의 단순화 |
| 파생값 처리 | 필요할 때 **계산(JOIN/집계)** | 미리 **계산해서 저장** |
| 쓰기 비용 | 낮음(한 군데만 고치면 됨) | 높음(원본 + 사본 동기화) |
| 읽기 비용 | 높음(매번 조인·집계) | 낮음(한 번의 속성 읽기) |
| 위험 | 느린 질의 | **이상 현상(anomaly), 값 불일치** |

정규화 이론의 핵심 규칙 중 하나가 "**다른 속성으로부터 계산 가능한(derivable) 속성은 저장하지 않는다**"이다.
`itemCount`, `subtotal`은 정확히 이 규칙을 어긴다. 어기는 것이 나쁘다는 뜻이 아니라,
**어긴 대가를 알고 감수하겠다는 선언**이 비정규화다.

### 그래프/온톨로지 맥락에서의 의미

관계형에서 비정규화는 "다른 테이블의 컬럼을 복사해 오기"인 경우가 많지만,
온톨로지에서는 "**간선을 따라 순회하면 얻을 수 있는 집계값을 노드 속성으로 굳혀 두기**"의 형태가 된다.

```gql
-- 정규화된 방식: 매번 순회 + 집계
MATCH (c:Cart {cartId: $id})-[:contains]->(p:Product)
RETURN count(p) AS itemCount, sum(p.price) AS subtotal

-- 비정규화된 방식: 한 노드만 읽으면 끝
MATCH (c:Cart {cartId: $id})
RETURN c.itemCount, c.subtotal
```

장바구니 배지("장바구니 3")는 사실상 모든 페이지 렌더링마다 필요하다.
매번 fan-out 순회를 하느니 노드 속성 하나를 읽는 편이 압도적으로 싸다.
Complete Platform 아티클의 질의 예시에서도 `Buyer → Cart (itemCount > 0) with no Buyer → Order`처럼
**`itemCount`를 필터 조건으로 바로 쓰고 있다** — 저장해 두었기에 인덱스를 걸고 스캔할 수 있다.

## 3. 대가: 갱신 이상(update anomaly)과 정합성

파생값을 저장하는 순간, **같은 사실이 두 곳에 존재**하게 된다(간선들 + 속성).
두 곳이 어긋나면 그 자체가 버그다. 전형적인 사고 사례:

- 카트에 상품을 추가했는데 `itemCount` 증가를 빠뜨림 → 배지와 실제 목록이 불일치
- 상품을 제거하는 경로가 여러 개(사용자 삭제, 재고 소진 자동 제거, 세션 만료)인데 일부 경로만 `subtotal`을 갱신
- **`Product.price`가 바뀌었을 때** — 카트 내용은 그대로인데 `subtotal`이 낡은 값이 됨(가장 놓치기 쉬운 케이스)
- 동시 요청 두 개가 각각 "읽고 +1 해서 쓰기"를 하면 lost update로 개수가 하나 모자람
- 부분 실패: 간선은 커밋됐는데 속성 갱신이 실패 → 영구 불일치

즉 비정규화의 비용은 디스크 몇 바이트가 아니라 **"모든 쓰기 경로가 이 값을 책임져야 한다"는 규율 비용**이다.

---

## 4. 갱신 전략

파생값을 최신으로 유지하는 방법은 대략 네 가지이며, 각각 신선도(freshness)와 비용이 다르다.

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **애플리케이션 로직** | 카트 서비스의 add/remove 함수 안에서 같이 갱신 | 단순, 트랜잭션 안에서 처리 가능 | 쓰기 경로가 늘어나면 누락 위험, 우회 경로(배치 스크립트)에 취약 |
| **DB 트리거 / 제약** | `contains` 삽입·삭제 시 트리거로 카운터 갱신 | 우회 불가, 강한 일관성 | DB 종속, 디버깅 어려움, 잠금 경합 |
| **이벤트 기반(CDC/이벤트 소싱)** | `ItemAddedToCart` 등의 이벤트를 구독해 읽기 모델(투영) 갱신 | 확장성, 쓰기 경로와 디커플링 | **최종 일관성**(잠깐 어긋남), 순서·중복 처리 필요 |
| **배치 재계산 / reconciliation** | 주기적으로 전체를 다시 계산해 덮어씀 | 드리프트 자동 치유, 구현 단순 | 지연이 큼, 단독 전략으로는 부족 |

실무에서는 보통 **"증분 갱신(1~3) + 주기적 재계산(4)"을 함께** 쓴다.
증분 갱신으로 신선도를 확보하고, 배치는 안전망(drift detector)으로 둔다.
"진실의 원천은 항상 `contains` 간선이고, `itemCount`/`subtotal`은 언제든 폐기·재생성 가능한 캐시"라는
원칙을 명시해 두면 사고 복구가 쉬워진다.

`subtotal`이 가격 변동에 영향받는 문제는 별도 결정이 필요하다.
(a) 가격 변경 이벤트를 구독해 영향받는 카트들을 갱신하거나,
(b) 카트는 "현재가 기준"임을 명시하고 체크아웃 직전에 반드시 재계산하거나(대부분의 실제 커머스가 이 방식),
(c) 카트 라인에 담을 때의 가격을 함께 저장한다.

## 5. 언제 비정규화가 정당한가 — 판단 기준

다음 조건이 많이 맞을수록 정당하다.

1. **읽기:쓰기 비가 크게 읽기 쪽으로 기운다.** 카트 요약은 페이지마다 읽히지만 변경은 가끔이다. ✅
2. **매번 계산하는 비용이 실제로 아프다.** 팬아웃이 크거나, 핫패스이거나, 여러 시스템(트랜잭션 DB / 검색 엔진 / 분석 웨어하우스)에 걸친 조인이 필요하다. 이 시나리오는 실제로 시스템이 나뉘어 있다. ✅
3. **파생 규칙이 안정적이고 단순하다.** 개수와 합계는 정의가 흔들리지 않는다. ✅
4. **약간의 지연/근사가 허용된다.** 카트 배지가 1초 늦어도 사업적으로 치명적이지 않다. ✅ (반면 결제 금액은 아니다.)
5. **갱신 경로를 한 곳으로 모을 수 있다.** 카트 변경이 단일 서비스를 통한다면 안전하다.
6. **원본으로부터 항상 재구성 가능하다.** 즉 이 값이 유일한 진실이 아니어야 한다.
7. **필터·정렬·집계 키로 쓰인다.** `itemCount > 0`처럼 질의 술어로 쓰려면 저장돼 있어야 인덱스가 붙는다. ✅

반대로 **피해야 할 때**: 쓰기가 매우 잦은데 읽기는 드물 때, 파생 규칙이 자주 바뀔 때,
불일치가 금전적/법적 손해로 직결되는데 강한 일관성을 보장할 수단이 없을 때.

원칙: **먼저 정규화하고, 측정된 병목에 한해 비정규화한다.** 그리고 비정규화한 속성에는
"이건 파생값이며 진실의 원천은 X다"라는 사실을 모델 문서에 반드시 남긴다.

## 6. Order의 `total`은? — 같은 파생값이지만 성격이 다르다

Core Marketplace의 Order 엔티티:

| Property | Type | Identifier? |
|---|---|---|
| `orderId` | string | ✓ |
| `orderDate` | datetime | |
| `status` | string | |
| `total` | decimal (USD) | |
| `shippingMethod` | string | |

`total` 역시 형식적으로는 `includes` 관계로 연결된 Product들의 가격 합이므로 **파생 속성처럼 보인다**.
그러나 결정적인 차이가 있다.

| | `Cart.subtotal` | `Order.total` |
|---|---|---|
| 대상 | 진행 중인 **세션 엔티티** (mutable) | 확정된 **거래 기록** (immutable) |
| 시간성 | "지금 이 순간"의 현재 상태 | 주문 확정 **시점의 스냅샷** |
| 재계산 가능? | 언제든 재계산 가능 — 재계산이 곧 정답 | **재계산하면 오히려 틀린 값이 나올 수 있음** |
| 저장 이유 | 성능 최적화(캐시) | **정확성·감사(audit) 요구 — 저장이 필수** |
| 버리면? | 아무 문제 없음(다시 만들면 됨) | 복구 불가능한 정보 손실 |

왜 `Order.total`은 재계산하면 안 되는가:

- 상품 가격은 **나중에 바뀐다.** 작년 주문을 오늘 가격으로 다시 더하면 실제 결제액과 달라진다.
- 쿠폰·할인·프로모션·세금·배송비·환율이 그 시점의 규칙으로 적용됐다.
- 상품이 **단종·삭제**될 수 있다. 간선이 사라지면 합계 자체를 만들 수 없다.
- 회계·세무·분쟁 대응상 "그때 실제로 청구한 금액"이 보존돼야 한다.

즉 `Order.total`은 비정규화가 아니라 **시간적 스냅샷(temporal snapshot) 또는 불변 사실의 기록**이다.
겉모습(집계값을 속성으로 들고 있다)은 같지만 정당화 근거가 다르다.

- `Cart.subtotal`: "계산할 수 있지만 **빠르려고** 저장한다" → 성능 트레이드오프, 불일치 시 재계산으로 치유.
- `Order.total`: "다시 계산할 수 없으니 **정확하려고** 저장한다" → 정합성 요구, 재계산은 금지에 가깝다.

같은 논리가 Review의 `verified`(구매 여부를 Order 경로로 검증할 수 있지만 그 시점 판정을 굳혀 둠)나
Buyer의 `totalSpent`(모든 Order를 합치면 나오는 값 — 이쪽은 전형적인 성능형 비정규화이며,
주문 확정 이벤트로 증분 갱신 + 배치 재계산이 잘 어울린다)에도 적용된다.

## 7. 기억할 문장

- 비정규화 = **"계산 가능한 값을 굳이 저장한다"** → 저장 공간·정합성 부담 ↔ 질의 속도.
- `itemCount`, `subtotal`은 `contains`로부터 유도 가능하지만 **핫패스 조회를 위해 저장**된 요약 속성이다.
- 저장한 순간부터 **모든 쓰기 경로가 갱신 책임**을 진다(트리거·이벤트·배치 재계산 중 택일 또는 조합).
- 같은 "집계 속성"이라도 `Order.total`은 **확정 시점 스냅샷**이라 저장이 최적화가 아니라 **요구사항**이다.

## 관련 카드

- Shopping-Cart가 세션 엔티티인 이유 / `has_cart`가 one-to-one인 이유
- Buyer의 `totalSpent`가 생애가치(LTV) 세그먼테이션을 가능하게 하는 이유
- Product의 `stockQty`로 재고 질의를 수행하는 방식

# SKU는 무엇의 약자이며 왜 Product의 식별자로 쓰이는가?

## 한 줄 정답

**SKU = Stock Keeping Unit(재고 관리 단위)**. 재고 관리·창고·e-commerce 시스템 전반에서 각 품목을 고유하게 식별하는 **업계 표준 식별자**이기 때문에, 새로 만든 `productId` 대신 `sku`를 Product의 identifier로 쓴다.

---

## 1. 학습 자료에서의 맥락

E-Commerce Platform 시나리오의 Step 1(Core Marketplace)에서 Product 엔티티는 다음과 같이 정의된다.

| Property | Type | Identifier? |
|---|---|---|
| `sku` | string | ✓ |
| `name` | string | |
| `category` | string | |
| `price` | decimal (USD) | |
| `stockQty` | integer | |

자료의 원문 설명은 이렇다.

> The identifier here is `sku` (Stock Keeping Unit) — the standard product identifier in e-commerce.

그리고 Scenario Overview에는 이 결정을 이해하는 데 결정적인 문장이 하나 더 있다.

> Data flows through multiple systems — a transactional database for orders, a search engine for product discovery, and an analytics warehouse for buyer behavior.

즉 이 플랫폼의 데이터는 **트랜잭션 DB / 검색 엔진 / 분석용 웨어하우스** 세 곳에 흩어져 있다. 이 세 시스템이 이미 공통으로 들고 있는 상품 키가 바로 SKU다. 온톨로지의 identifier는 "여러 소스 시스템을 하나의 노드로 묶어주는 접착제" 역할을 하므로, **이미 모든 소스에 존재하는 키**를 고르는 것이 새 키를 발명하는 것보다 압도적으로 유리하다.

## 2. SKU의 실체: 무엇을 세는 단위인가

"Stock Keeping Unit"을 직역하면 **재고를 유지(keeping)하는 단위(unit)** 다. 이름 자체가 정의다.

- **판매자가 직접 부여**한다. 소매업체·브랜드가 자기 창고와 카탈로그 기준으로 만든다.
- **영숫자 조합**이 일반적이다. 보통 8~12자 내외이며 형식 규정이 없다. 예: `TSHIRT-BLK-M`, `NB-990V6-GRY-270`.
- **변형(variant) 단위**로 매겨진다. 이 점이 핵심이다. "티셔츠"는 상품이지만, **블랙/M 티셔츠와 블랙/L 티셔츠는 서로 다른 SKU**다. 창고에서 따로 쌓고 따로 세야 하기 때문이다.
- **판매자 범위 안에서만 고유**하다. A 쇼핑몰의 `SKU-1001`과 B 쇼핑몰의 `SKU-1001`은 아무 관계가 없다.

### 그래서 `stockQty`가 SKU와 짝을 이룬다

자료에서 Product가 `stockQty` 속성을 갖는 것은 우연이 아니다. **재고 수량을 셀 수 있는 최소 단위 = SKU**이므로, `sku`를 identifier로 잡는 순간 `stockQty`가 자연스럽게 해당 노드의 속성이 된다. 만약 identifier를 "모델 단위"로 잡았다면 재고 수량은 사이즈·색상별로 쪼개져야 해서 단일 정수 속성으로 표현할 수 없다.

> **정리:** identifier 선택은 단순한 이름 짓기가 아니라 **엔티티의 입도(granularity)를 결정하는 행위**다. SKU를 고르면 Product 노드 하나 = 재고 단위 하나가 된다.

## 3. 다른 상품 식별자 체계와의 비교

SKU만 있는 게 아니다. 실무에서는 여러 식별자가 동시에 존재하며, **누가 발급하는가**가 가장 중요한 구분선이다.

| 식별자 | 정식 명칭 | 발급 주체 | 형식 | 고유성 범위 |
|---|---|---|---|---|
| **SKU** | Stock Keeping Unit | 판매자/소매업체 자체 | 영숫자, 형식 자유 | 해당 판매자 내부 |
| **GTIN** | Global Trade Item Number | GS1 (국제 표준화 기구) | 숫자 8/12/13/14자리 | 전 세계 |
| **UPC** | Universal Product Code | GS1 US | 숫자 12자리 (= GTIN-12) | 전 세계, 주로 북미 |
| **EAN** | (European→International) Article Number | GS1 | 숫자 13자리 (= GTIN-13) | 전 세계, 유럽·아시아 중심 |
| **ISBN** | International Standard Book Number | ISBN 기관 | 13자리 (978/979 접두) | 전 세계, 도서 |
| **ASIN** | Amazon Standard Identification Number | Amazon | 영숫자 10자리 | Amazon 플랫폼 내부 |
| **MPN** | Manufacturer Part Number | 제조사 | 영숫자, 형식 자유 | 해당 제조사 내부 |

### 3-1. GTIN 우산 아래의 UPC / EAN

**GTIN은 개별 코드가 아니라 우산 개념**이다. GS1이 정의한 상품 식별 번호 체계의 총칭이며, 자릿수에 따라 하위 형태가 나뉜다.

- **GTIN-12 = UPC-A** — 12자리. 북미 소매의 기본. 1974년 오하이오 마트에서 껌 한 통이 최초로 스캔된 그 바코드다.
- **GTIN-13 = EAN-13** — 13자리. 유럽·아시아 포함 국제 표준. 앞 3자리는 GS1 국가/지역 프리픽스(한국은 880).
- **GTIN-8 = EAN-8** — 포장이 작아 13자리를 못 넣는 소형 품목용.
- **GTIN-14** — 낱개가 아니라 **박스·팔레트 같은 물류 포장 단위**에 붙는다.

모든 GTIN은 마지막 자리가 **체크 디지트**여서 오타·오독을 산술적으로 검출할 수 있다. SKU에는 이런 검증 장치가 없다.

ISBN-13도 사실 GTIN-13이다. `978`/`979` 프리픽스(별칭 "Bookland")를 쓰는 도서 전용 슬롯이다.

### 3-2. ASIN — 플랫폼 사설 식별자

ASIN은 Amazon이 자기 카탈로그를 위해 발급하는 10자리 영숫자 키다. 도서의 경우 ASIN이 ISBN-10과 동일하게 부여된다. **표준이 아니라 특정 플랫폼의 사설 식별자**라는 점에서, 성격상 GTIN보다는 "규모가 아주 큰 SKU"에 가깝다.

### 3-3. 핵심 대비: 발급 주체가 결정하는 모든 것

```
제조사/GS1이 발급  →  GTIN(UPC/EAN)  →  "이 물건이 세상에서 무엇인가"   (조직 간 공유 가능)
판매자가 발급      →  SKU            →  "내 창고에서 이걸 어떻게 세는가" (조직 내부 최적화)
```

같은 코카콜라 500ml 캔은 **전 세계에서 GTIN이 하나**지만, 그것을 파는 100개 쇼핑몰에는 **100개의 서로 다른 SKU**가 존재한다. 반대로 판매자가 만든 3개 상품 묶음 세트나 자체 제작(PB) 상품에는 **GTIN이 아예 없을 수 있지만 SKU는 반드시 있다.**

이 비대칭 때문에 실무 카탈로그는 보통 두 키를 **모두** 보관한다. SKU를 primary key로 쓰고, GTIN은 외부 채널(오픈마켓 연동, 가격 비교, 바코드 스캔)과 매핑하기 위한 보조 키로 둔다.

## 4. 그래서 왜 `productId`가 아니라 `sku`인가

퀴즈 오답 선지들("SKU가 타이핑하기 짧아서", "productId는 이름 충돌이 나서", "SKU는 항상 숫자라서")은 전부 표면적인 이유다. 진짜 이유는 네 가지다.

### (1) 이미 존재하는 키다 — 발명 대신 채택

`productId`는 이 온톨로지를 위해 **새로 만들어야 하는 키**다. 새 키를 만들면 트랜잭션 DB·검색 엔진·웨어하우스 각각에 대해 `productId ↔ 각 시스템의 상품 키` 매핑 테이블을 유지해야 한다. 매핑 테이블은 언젠가 반드시 어긋난다. SKU를 쓰면 매핑 계층 자체가 사라진다.

### (2) 조직 공통 언어다

창고 담당자, MD, CS 상담원, 물류 파트너가 모두 SKU로 대화한다. 온톨로지의 목적은 "여러 시스템·여러 부서가 같은 개념을 같은 이름으로 부르게 하는 것"이므로, 이미 조직이 쓰는 어휘를 identifier로 승격시키는 것이 온톨로지 철학에 정확히 부합한다.

### (3) 사람이 읽을 수 있다 (human-readable)

쿼리 결과에 `sku = "NB-990V6-GRY-270"`이 찍히면 무엇인지 바로 안다. `productId = "a3f9c1e2-..."` 가 찍히면 다시 조인해야 한다. 디버깅·데이터 검증·수작업 대조 비용이 확연히 다르다.

### (4) 외부 시스템과 그대로 연결된다

주문서, 송장, WMS 피킹 리스트, 반품 라벨에 인쇄되는 값이 SKU다. 온톨로지 identifier가 이 값과 같으면 시스템 경계를 넘는 추적이 무료로 따라온다.

## 5. 온톨로지에서 natural key를 identifier로 쓴다는 것의 함의

여기가 이 카드의 진짜 교훈이다. SKU는 **natural key(자연 키, 업무 키)** 이고, UUID나 자동 증가 정수는 **surrogate key(대리 키)** 다.

### 5-1. 온톨로지에서 identifier는 곧 "동일성(identity)"이다

관계형 DB에서 PK는 행을 찾는 수단에 가깝지만, 온톨로지/그래프에서 identifier는 더 무겁다.

- **머지(merge) 규칙이다.** 서로 다른 소스에서 들어온 두 레코드의 `sku`가 같으면 **같은 노드**가 된다. 다르면 **다른 노드**다. identifier가 곧 "이 둘은 같은 것인가?"에 대한 시스템의 답이다.
- **관계의 종착점이다.** `Order -includes-> Product`, `Shopping-Cart -contains-> Product`, `Review -reviews-> Product` 이 세 관계가 전부 `sku` 값을 통해 Product 노드에 연결된다. SKU 하나가 흔들리면 세 관계가 동시에 끊긴다.
- **입도를 확정한다.** 3절에서 본 것처럼 "Product 노드 하나 = 재고 단위 하나"라는 모델의 의미론이 SKU 선택에서 파생된다.

### 5-2. natural key의 장점

| 장점 | 설명 |
|---|---|
| **조인 무비용** | 소스 시스템이 이미 그 값을 갖고 있어 매핑 테이블 없이 바로 붙는다 |
| **가독성** | 사람이 읽고 검증할 수 있어 데이터 품질 문제를 눈으로 잡아낸다 |
| **의미 보존** | 값 자체가 업무적 의미를 지녀 온톨로지가 현실을 그대로 반영한다 |
| **외부 연동** | 송장·바코드·파트너 API와 동일한 값이라 경계를 넘어 추적된다 |

### 5-3. natural key의 위험 — 반드시 알아야 할 것들

natural key는 공짜가 아니다. **"업무가 바뀌면 키도 바뀐다"** 는 근본적 취약점을 갖는다.

1. **변경 가능성(mutability)**
   카탈로그 마이그레이션, 회사 합병, ERP 교체 때 SKU 체계를 통째로 재부여하는 일이 실제로 벌어진다. identifier가 바뀌면 그 노드를 가리키던 **모든 관계가 고아가 된다.** surrogate key였다면 SKU는 단순 속성이므로 값만 업데이트하면 끝난다.

2. **재사용(reuse) — 가장 위험한 함정**
   단종된 상품의 SKU를 몇 년 뒤 다른 상품에 재할당하는 관행이 흔하다. 그러면 **2019년 주문과 2026년 주문이 같은 Product 노드에 붙어버린다.** 과거 매출 분석과 리뷰가 엉뚱한 상품에 귀속되는, 조용하고 치명적인 오염이다.

3. **고유성 범위의 함정 — 멀티벤더 마켓플레이스**
   이 시나리오는 "general-purpose e-commerce **marketplace**"다. 즉 여러 판매자가 입점할 수 있다. SKU는 판매자 내부에서만 고유하므로, **판매자 A의 `SKU-1001`과 판매자 B의 `SKU-1001`이 하나의 노드로 잘못 머지된다.** 실무 해법은 네임스페이스를 붙여 복합 키로 만드는 것이다.
   ```
   sku:  "SKU-1001"                 ← 충돌 가능
   id:   "seller-42:SKU-1001"       ← 판매자 네임스페이스로 격리
   ```
   학습용 단일 판매자 모델에서는 `sku` 단독으로 충분하지만, 규모가 커지면 이 지점이 첫 번째로 깨진다.

4. **스마트 키(smart key) 문제**
   `TSHIRT-BLK-M`처럼 SKU 문자열에 카테고리·색상·사이즈를 인코딩하는 관행이 널리 쓰인다. 편리하지만, **속성이 키 안에 숨어버려** 색상 표기 규칙이 바뀌면 키가 바뀐다. 온톨로지에서는 그런 정보를 `category`, `color`, `size` 같은 **독립 속성으로 꺼내 두고** 키는 불투명하게 유지하는 편이 안전하다.

5. **정규화(normalization) 부담**
   `sku-1001`, `SKU-1001`, `SKU 1001`, `0001001`(선행 0 유실)은 사람 눈에는 같지만 시스템에는 서로 다른 노드다. natural key를 쓰는 순간 **대소문자·공백·하이픈·선행 0에 대한 정규화 규칙을 명시적으로 정해야 한다.**

6. **정보 노출**
   순번 기반 SKU는 총 취급 품목 수나 신상품 출시 속도를 외부에 노출할 수 있다.

### 5-4. 실무 절충안: 이중 키 전략

성숙한 온톨로지는 대개 둘 중 하나를 고르지 않고 **둘 다 쓴다.**

```
Product
├─ id      : 불변 surrogate key (UUID)   ← 그래프 내부 관계가 물리적으로 참조
├─ sku     : natural / business key       ← 조회·조인·사람이 쓰는 키, unique 제약
└─ gtin    : 글로벌 표준 키 (선택)         ← 외부 조직·채널과의 연동
```

- 그래프 내부 참조는 절대 바뀌지 않는 surrogate가 담당한다 → 재부여·합병에 안전.
- SKU는 **alternate key / unique 제약**으로 남겨 소스 시스템 조인과 사람의 조회를 담당한다.
- GTIN이 있으면 조직 간 페더레이션(가격 비교, 파트너 카탈로그 매칭)의 앵커로 쓴다.

학습 경로의 모델이 `sku` 단독을 identifier로 삼은 것은 **"온톨로지 identifier는 현실 업무의 키를 채택해야 한다"** 는 원칙을 가장 선명하게 보여주기 위한 선택이다. 실제 프로덕션에서는 위 이중 키 구조로 확장되는 것이 일반적이다.

## 6. 좋은 identifier의 체크리스트

SKU가 왜 통과했는지 항목별로 확인해 보자.

| 기준 | 설명 | SKU |
|---|---|---|
| **Unique (고유)** | 범위 안에서 중복 없음 | ✓ (단, 판매자 범위 한정) |
| **Non-null (필수)** | 모든 인스턴스가 값을 가짐 | ✓ 재고를 세려면 반드시 존재 |
| **Stable (안정)** | 시간이 지나도 안 바뀜 | △ 재부여·재사용 위험 |
| **Available (가용)** | 모든 소스 시스템에 존재 | ✓ DB·검색·웨어하우스 전부 보유 |
| **Readable (가독)** | 사람이 이해 가능 | ✓ |

`productId`는 Unique/Non-null/Stable은 만족하지만 **Available에서 탈락**한다. 어느 소스 시스템에도 존재하지 않기 때문이다. 이것이 SKU가 이기는 결정적 지점이다.

## 7. 다른 엔티티의 identifier와 비교해 보기

같은 온톨로지의 나머지 엔티티는 모두 `~Id` 패턴을 쓴다.

| 엔티티 | Identifier | 성격 |
|---|---|---|
| Buyer | `buyerId` | 시스템 발급 (surrogate 성격) |
| **Product** | **`sku`** | **업계 표준 natural key** |
| Order | `orderId` | 시스템 발급 |
| Shopping-Cart | `cartId` | 시스템 발급 (세션 엔티티) |
| Review | `reviewId` | 시스템 발급 |

Product만 예외인 이유는 명확하다. **Product만이 조직 외부(창고, 물류, 제조사, 바코드)에 실물로 존재하는 개체**다. Order·Cart·Review는 이 플랫폼 안에서 태어나 이 플랫폼 안에서만 사는 레코드이므로 외부 표준 키가 애초에 없다.

> **일반화된 규칙:** 실물 세계 또는 조직 외부에 이미 표준 식별자가 존재하는 엔티티는 그것을 채택하고(SKU, ISBN, 사업자등록번호, VIN, IATA 공항 코드), 시스템 내부에서 생성되는 엔티티는 시스템이 발급한 키를 쓴다.

## 8. 암기 포인트

- **SKU = Stock Keeping Unit**, "재고를 유지하는 단위". 이름이 곧 정의다.
- **판매자가 발급**하는 natural key. 형식 자유, 영숫자, **변형(사이즈/색상) 단위**.
- **GTIN/UPC/EAN는 GS1이 발급**하는 전 세계 고유 표준. UPC = GTIN-12(12자리), EAN = GTIN-13(13자리). **ASIN은 Amazon 사설 키.**
- `productId` 대신 SKU를 쓰는 이유는 **이미 모든 소스 시스템에 존재하는 조직 공통 키**이기 때문이다. 짧아서도, 숫자여서도 아니다.
- 온톨로지에서 identifier는 **노드의 동일성·머지 규칙·엔티티 입도**를 동시에 결정한다.
- natural key의 대가는 **변경·재사용·범위 충돌·정규화**. 실무에서는 불변 surrogate + SKU(alternate key) + GTIN(연동 키)의 **이중/삼중 키 구조**로 푼다.

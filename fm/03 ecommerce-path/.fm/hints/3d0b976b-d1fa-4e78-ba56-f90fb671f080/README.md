# 왜 `<-[:reviews]-` 는 화살표가 반대일까?

## 문제의 질의

Complete Platform 단계에서 등장하는 GQL 예시는 "지금 누군가의 장바구니에 담겨 있는 상품에 달린 인증(verified) 리뷰"를 찾는다.

```gql
MATCH (b:Buyer)-[:has_cart]->(c:Cart)-[:contains]->(p:Product)<-[:reviews]-(r:Review)
WHERE r.verified = true
RETURN p.name, r.rating, r.title
```

앞의 두 엣지는 `->` 인데 마지막 하나만 `<-` 다. 오타가 아니라, 스키마에 정의된 방향을 그대로 따른 결과다.

## 1. 정의 방향(스키마)과 탐색 방향(질의)은 별개다

이 온톨로지의 6개 관계는 모두 **방향을 가진 채로 정의**되어 있다.

| 관계 | 정의 방향 | 카디널리티 |
|---|---|---|
| `places` | `Buyer → Order` | one-to-many |
| `includes` | `Order → Product` | many-to-many |
| `has_cart` | `Buyer → Shopping-Cart` | one-to-one |
| `contains` | `Shopping-Cart → Product` | many-to-many |
| `writes` | `Buyer → Review` | one-to-many |
| **`reviews`** | **`Review → Product`** | many-to-one |

여기서 두 가지를 분리해서 생각해야 한다.

- **정의 방향 (storage / schema direction)**: 엣지가 어느 노드에서 나가 어느 노드로 들어가는지. 그래프 DB는 엣지를 **한 방향으로만 저장**한다. `reviews` 엣지의 꼬리(tail)는 `Review`, 머리(head)는 `Product`다.
- **탐색 방향 (traversal direction)**: 질의가 실제로 어느 노드에서 출발해 어느 노드로 이동하는지. 저장은 단방향이지만 **순회는 양방향으로 가능**하다. 대부분의 그래프 엔진은 각 노드에 대해 나가는 엣지(outgoing)와 들어오는 엣지(incoming)를 모두 인덱싱해 두므로, 들어오는 엣지를 거슬러 올라가는 것도 나가는 엣지를 따라가는 것과 동일한 비용이다.

즉 `<-` 는 "관계가 반대로 정의됐다"는 뜻이 **아니라**, "이 지점에서는 정의된 방향의 **반대로 순회하겠다**"는 표시다. 화살표는 스키마를 다시 선언하는 게 아니라, 지금 읽고 있는 경로가 그 엣지를 어느 쪽으로 지나가는지를 표기하는 것이다.

## 2. 화살표 방향을 판단하는 절차

질의문의 경로를 **왼쪽에서 오른쪽으로** 읽으면서, 각 엣지마다 아래 세 단계를 적용하면 된다.

1. **이 엣지의 왼쪽 노드와 오른쪽 노드가 무엇인지 확인한다.**
2. **스키마에서 그 관계의 정의 방향(출발 라벨 → 도착 라벨)을 떠올린다.**
3. **정의의 출발점이 왼쪽에 있으면 `-[:rel]->`, 오른쪽에 있으면 `<-[:rel]-`.**

예시 질의에 적용하면:

| 구간 | 왼쪽 | 오른쪽 | 정의 방향 | 정의의 출발점 위치 | 표기 |
|---|---|---|---|---|---|
| 1 | `b:Buyer` | `c:Cart` | Buyer → Cart | 왼쪽 | `-[:has_cart]->` |
| 2 | `c:Cart` | `p:Product` | Cart → Product | 왼쪽 | `-[:contains]->` |
| 3 | `p:Product` | `r:Review` | **Review → Product** | **오른쪽** | `<-[:reviews]-` |

세 번째 구간에서 문장은 `Product`를 이미 지나온 뒤 `Review`로 향한다. 그런데 `reviews`의 정의는 `Review → Product`다. 정의상 도착지(Product)에서 출발지(Review)로 되돌아가는 셈이므로 화살표는 왼쪽을 향한다.

기억하기 좋은 문장: **"화살표는 내가 걷는 방향이 아니라, 엣지가 원래 가리키는 방향을 그린다."** 왼쪽에서 오른쪽으로 걸어가는 동안 엣지가 나를 마주 보고 있으면 `<-`가 된다.

## 3. 같은 질의를 다르게 써도 동치인 이유

아래 세 질의는 **정확히 같은 결과 집합**을 만든다.

```gql
-- (A) 원본: Buyer에서 출발
MATCH (b:Buyer)-[:has_cart]->(c:Cart)-[:contains]->(p:Product)<-[:reviews]-(r:Review)

-- (B) Review에서 출발
MATCH (r:Review)-[:reviews]->(p:Product)<-[:contains]-(c:Cart)<-[:has_cart]-(b:Buyer)

-- (C) Product를 가운데 두고 두 갈래로 쪼갬
MATCH (b:Buyer)-[:has_cart]->(c:Cart)-[:contains]->(p:Product),
      (r:Review)-[:reviews]->(p:Product)
```

동치인 이유는 이렇다. `MATCH` 패턴이 기술하는 것은 **그래프 안의 부분그래프(subgraph) 모양**이지, 방문 순서가 아니다. 세 질의 모두 "Buyer -has_cart→ Cart -contains→ Product ←reviews- Review" 라는 동일한 모양을 서술한다. 패턴을 뒤집어 쓰면 각 엣지의 좌우 노드가 바뀌므로 화살표 표기도 전부 함께 뒤집히고(`->` ↔ `<-`), 결과적으로 가리키는 실제 엣지는 그대로다. (B)에서 `-[:reviews]->`가 `->`인 이유가 바로 이것이다 — 이제 Review가 왼쪽에 있기 때문이다.

### 그렇다면 시작 노드 선택은 왜 중요한가

결과는 같아도 **실행 계획(execution plan)과 비용은 다를 수 있다.** 옵티마이저는 보통 다음을 고려해 앵커(시작점)를 고른다.

- **선택도(selectivity)**: 가장 적은 후보 노드로 좁혀지는 지점에서 시작하는 게 유리하다. 예시 질의에는 `WHERE r.verified = true` 조건이 있으므로, verified 리뷰가 전체 리뷰의 일부라면 `Review`에서 출발해 `reviews`를 따라 Product로 가는 (B) 형태가 실제로는 더 적은 중간 결과를 만들 수 있다.
- **인덱스 활용**: `p.sku = 'X'` 같은 동등 조건이 있으면 그 노드가 인덱스 시크로 즉시 잡히므로 앵커가 되기 쉽다.
- **팬아웃(fan-out)**: 카디널리티를 보라. `reviews`는 many-to-one이다. Product 하나에서 역방향으로 펼치면 리뷰가 수천 개로 팬아웃되지만, Review에서 정방향으로 가면 항상 정확히 1개의 Product로 수렴한다. 팬아웃이 큰 방향은 뒤로 미루는 편이 중간 결과를 작게 유지한다.
- **양방향/중간 확장**: (C)처럼 Product를 조인 포인트로 명시하면 옵티마이저가 양쪽에서 각각 확장해 Product에서 만나는 계획을 세우기 쉬워진다.

성숙한 엔진은 통계를 보고 알아서 재정렬하므로 대개는 읽기 좋은 순서로 쓰면 된다. 다만 **"방향 표기는 의미(어떤 엣지를 매칭할지), 작성 순서는 힌트(어떻게 실행할지)"** 라는 구분은 기억해 둘 만하다. 방향을 잘못 쓰면 결과가 틀리고, 순서를 어색하게 쓰면 결과는 맞되 느려진다.

## 4. 능동형 동사 이름이 방향을 자기설명적으로 만든다

이 온톨로지의 관계 이름은 모두 **주어가 앞 노드인 능동형 3인칭 동사**다.

- `Buyer` **writes** `Review` — "구매자가 리뷰를 쓴다"
- `Buyer` **places** `Order` — "구매자가 주문을 넣는다"
- `Review` **reviews** `Product` — "리뷰가 상품을 리뷰한다"
- `Cart` **contains** `Product` — "장바구니가 상품을 담고 있다"

이렇게 지으면 `(A)-[:rel]->(B)` 를 **"A rel B"라는 영어 문장으로 그대로 읽을 수 있다.** 이름 자체가 방향의 문서 역할을 하므로, 화살표가 어느 쪽이어야 하는지 스키마를 다시 열어보지 않아도 대개 짐작이 간다. 반대로 `productReview`, `buyerOrder` 같은 명사형이나 `link`, `relatedTo` 같은 모호한 이름은 방향 정보를 전혀 담지 못한다.

혼동하기 쉬운 지점: `reviews`라는 이름은 "리뷰들"이라는 복수 명사로도 읽힌다. `Product`에 붙은 리뷰 목록처럼 들려서 `Product → Review` 방향이라고 착각하기 쉽다. 실제 정의는 동사로서 `Review → Product`(many-to-one, 리뷰 하나는 정확히 상품 하나에 대한 것)이다. 이런 애매함 때문에 팀에 따라 `reviewsProduct`, `about`, `targets` 같이 더 명시적인 이름을 쓰기도 한다.

### 역방향 이름(inverse property)을 따로 두는 설계와의 비교

또 다른 접근은 **역관계에 이름을 따로 부여**하는 것이다.

- OWL: `owl:inverseOf` — `:writtenBy owl:inverseOf :writes` 를 선언하면, 추론기가 `?b :writes ?r` 로부터 `?r :writtenBy ?b` 를 자동으로 도출한다.
- RDF/SPARQL: 스키마에 역속성이 없어도 프로퍼티 경로 `^:reviews` 로 역방향 순회를 표기할 수 있다(`?p ^:reviews ?r`). 이는 GQL/Cypher의 `<-` 에 대응한다.
- RDFS/스키마 도구, ORM: `inverse`, `mappedBy`, `belongs_to` / `has_many` 짝처럼 양방향 접근자를 함께 정의하는 관례.

두 설계의 트레이드오프:

| | 능동형 단일 이름 + 역방향 순회 (`<-`) | 역방향 이름을 별도 정의 (`owl:inverseOf` 등) |
|---|---|---|
| 저장 | 엣지 1개, 사실이 한 곳에만 존재 | 논리적으로는 1개 사실, 이름은 2개 |
| 어휘 | 최소한 — 익힐 이름이 적다 | 풍부 — 양쪽 관점에서 자연스러운 문장 |
| 일관성 위험 | 없음 | 두 이름을 물리적으로 중복 저장하면 동기화 어긋남 위험 |
| 질의 가독성 | `<-` 표기를 읽을 줄 알아야 함 | `(p)-[:reviewedBy]->(r)` 처럼 항상 정방향으로 쓸 수 있음 |
| 추론 | 없음 | 추론기가 역방향 트리플을 도출 (OWL DL) |

핵심은 **역방향 이름이 새로운 사실을 추가하지 않는다**는 점이다. 같은 엣지에 붙은 두 번째 라벨일 뿐이다. 그래서 속성 그래프 진영은 대체로 관계 이름을 하나만 두고 질의에서 `<-` 로 해결하는 쪽을, 온톨로지/추론 진영은 표현력과 자연어 대응을 위해 inverse property를 명시하는 쪽을 선호한다. 이 학습 경로의 온톨로지는 전자를 택했고, 그 결과가 `<-[:reviews]-` 다.

## 5. 방향을 무시한 매칭(`-[:reviews]-`)은 왜 위험한가

대부분의 그래프 질의 언어는 화살표를 생략한 무방향 패턴 `-[:reviews]-` 를 허용한다. "방향을 몰라도 되니 편하다"는 이유로 쓰기 쉽지만, 다음 문제가 있다.

- **의미가 뭉개진다.** 무방향 매칭은 "정방향 **또는** 역방향"의 합집합이다. 이 온톨로지에서는 `reviews`가 Review→Product 한 방향으로만 존재하므로 결과가 우연히 같지만, 데이터에 양방향 엣지가 섞여 들어오는 순간 조용히 의미가 달라진다.
- **대칭이 아닌 관계를 대칭처럼 다루게 된다.** `places`, `writes`, `contains`, `includes`는 모두 비대칭이다. 방향을 지우면 "주문을 넣은 구매자"와 "구매자를 넣은 주문"을 구별할 수 없다. 진짜로 대칭인 관계(`marriedTo`, `siblingOf` 같은)에서만 무방향이 의미상 정당하다.
- **경로가 길어지면 오탐이 폭증한다.** 여러 홉을 무방향으로 매칭하면 "Product에서 Review로 갔다가 다시 Product로" 같이 의도하지 않은 지그재그 경로가 잡힌다. 자기 참조 관계나 사이클이 있는 그래프에서는 결과 수가 급격히 늘고, 최악의 경우 경로 탐색이 끝나지 않는다.
- **성능이 나빠진다.** 옵티마이저가 각 노드에서 outgoing과 incoming 인접 리스트를 **양쪽 다** 확장해야 하므로 팬아웃이 커지고, 방향 정보에 기반한 카디널리티 추정이 무력화되어 계획 품질도 떨어진다.
- **버그가 조용히 숨는다.** 잘못된 방향으로 썼다면 `->`/`<-`를 쓴 질의는 보통 빈 결과를 돌려주어 즉시 오류를 알려준다. 무방향은 틀린 방향까지 함께 매칭해 주기 때문에 실수를 덮어버린다. **빈 결과는 진단 신호다.**

결론: 방향이 확실하지 않아서 `-[:reviews]-` 를 쓰고 싶어진다면, 그건 무방향을 쓸 이유가 아니라 **스키마를 확인할 이유**다.

## 한 줄 요약

`reviews`가 스키마에서 `Review → Product`로 정의됐고 질의는 `Product`에 먼저 도달하므로, 그 엣지를 거슬러 올라간다는 뜻으로 `<-[:reviews]-` 를 쓴다. 엣지는 한 방향으로 저장되지만 순회는 양방향 모두 가능하며, 화살표는 "내가 이동하는 방향"이 아니라 "엣지가 원래 가리키는 방향"을 그린 것이다.

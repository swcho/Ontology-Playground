# 왜 피드백 루프가 선형 체인보다 나은가?

> **Answer**
> 선형 체인은 한 방향 경로만 제공하지만, 루프는 같은 두 노드를 잇는 서로 다른 경로를 만들어 경로 간 존재/부재를 비교하는 질의를 가능하게 한다.

---

## 1. 선형 체인만 있을 때: 표현 가능한 질문의 천장

Step 1의 그래프는 딱 이것뿐이다.

```
Buyer --places--> Order --includes--> Product
```

Buyer에서 Product로 가는 방법이 **정확히 하나**다. 이 구조에서 물어볼 수 있는 건 결국 세 부류로 수렴한다.

| 유형 | 예시 | 본질 |
|---|---|---|
| 경로를 따라가기 (traversal) | "이 구매자가 산 상품 목록" | 경로 존재 → 나열 |
| 경로 위에서 집계 (aggregate) | "카테고리별 매출", "구매자별 주문 수" | 경로 존재 → 세기/합치기 |
| 경로 위 속성으로 필터 (filter) | "3월 이후 배송완료된 주문의 상품" | 노드/엣지 속성 조건 |

여기서 **부정 질의(negation)** 를 걸어봐야 나오는 답은 하나뿐이다 — "Buyer→Order→Product 경로가 없다" = **"이 상품을 산 적이 없다"**. 그런데 "산 적 없다"는 사실상 전체 구매자의 대부분이라서 정보량이 거의 0이다. 아무 맥락 없이 "이 상품을 안 산 사람"을 뽑으면 세상 사람 전부가 나온다.

즉 단일 경로 그래프의 한계는 이렇게 요약된다.

- 비교 대상이 없다. 경로가 하나면 "있다/없다" 두 상태뿐이고, **"있는데 다른 쪽은 없다"** 같은 상태를 만들 수 없다.
- 의도(intent)와 결과(outcome)를 구분할 수 없다. 주문은 "결과"만 기록한다. 사고 싶었지만 안 산 것, 사지 않았는데 의견을 남긴 것은 그래프에 자리가 없다.
- 부정 질의가 무의미하게 넓다. 대조군이 없으니 "없음"이 흥미로운 집단을 특정하지 못한다.
- 새 질문이 생기면 모델이 아니라 **애플리케이션 코드/ETL**로 도망가게 된다. "장바구니에만 담긴 상품"은 그래프 밖 로그 테이블을 뒤져야 한다.

## 2. 대체 경로가 생기면 왜 표현력이 계단식으로 늘어나는가

Step 3까지 오면 Buyer에서 Product로 가는 길이 **셋**이 된다.

```
Buyer --places----> Order   --includes--> Product     (구매 = 결과)
Buyer --has_cart--> Cart    --contains--> Product     (관심 = 의도)
Buyer --writes----> Review  --reviews---> Product     (의견 = 사후 반응)
```

핵심은 세 경로가 **같은 두 끝점(Buyer, Product)** 을 잇는다는 점이다. 끝점이 같으므로 세 경로의 결과 집합을 **같은 (구매자, 상품) 쌍의 좌표계 위에서 비교**할 수 있다.

여기서 표현력이 선형이 아니라 **지수적(계단식)** 으로 늘어난다.

- 경로가 1개면 상태는 2가지 (있음/없음) → 의미 있는 조합 1개
- 경로가 2개면 상태는 2² = 4가지 → 의미 있는 조합 3개 (교집합, 좌차집합, 우차집합)
- 경로가 3개면 상태는 2³ = 8가지 → 의미 있는 조합 7개
- 일반화하면 경로 n개에 대해 **2ⁿ − 1**개의 비어 있지 않은 벤 다이어그램 영역

경로 하나 추가는 노드 하나 추가지만, 질문의 개수는 곱하기 2가 된다. 이것이 "루프가 선형 체인보다 낫다"의 정량적 실체다. 학습 아티클의 표현대로 *"Feedback loops create richer query paths than linear chains."*

### 2-1. 두 경로만 있을 때의 유형 분류 (Order vs Review)

가장 교과서적인 2×2다. 각 칸이 그대로 다른 비즈니스 액션에 대응한다.

| | 리뷰 씀 (writes→reviews) | 리뷰 안 씀 |
|---|---|---|
| **구매함 (places→includes)** | 정상 검증 리뷰 → `verified = true` 근거, 신뢰 뱃지 | **리뷰 미작성 구매자** → 리뷰 요청 리마인드 발송 대상 |
| **구매 안 함** | **사지 않고 리뷰한 계정** → 어뷰징/가짜 리뷰 의심, 심사 큐 | 무관(대부분) — 정보량 없음 |

아티클 첫머리의 질문 *"Which verified reviewers rated products they didn't purchase?"* 가 바로 좌하단 칸이며, 그래프 패턴으로는 **"`writes → Review → reviews → Product` 경로는 있고, 동일 Product에 대해 `places → Order → includes → Product` 경로는 없다"** 로 표현된다. 경로가 하나뿐이던 Step 1에서는 이 질문 자체를 **쓸 수 없었다**.

```gql
-- 사지 않고 리뷰한 구매자 (가짜 리뷰 의심)
MATCH (b:Buyer)-[:writes]->(r:Review)-[:reviews]->(p:Product)
WHERE NOT EXISTS {
  MATCH (b)-[:places]->(:Order)-[:includes]->(p)
}
RETURN b.buyerId, p.sku, r.rating, r.verified
```

```gql
-- 샀는데 리뷰가 없는 구매자 (리뷰 요청 리마인드 대상)
MATCH (b:Buyer)-[:places]->(o:Order)-[:includes]->(p:Product)
WHERE o.status = 'DELIVERED'
  AND NOT EXISTS {
    MATCH (b)-[:writes]->(:Review)-[:reviews]->(p)
  }
RETURN b.email, p.name, o.orderDate
```

### 2-2. 세 경로일 때의 8가지 상태

Cart까지 넣으면 (Buyer, Product) 쌍마다 **(담음?, 삼?, 리뷰함?)** 이라는 3비트 상태가 붙는다.

| # | Cart | Order | Review | 해석 / 액션 |
|---|:---:|:---:|:---:|---|
| 0 | ✗ | ✗ | ✗ | 접점 없음. 추천 후보(cold) |
| 1 | ✓ | ✗ | ✗ | **장바구니 이탈(cart abandonment)** — 담아뒀지만 안 삼. 리마인드 메일·쿠폰, 재고/가격 알림 |
| 2 | ✗ | ✓ | ✗ | 구매했지만 리뷰 없음 — **리뷰 요청 리마인드** (즉시구매 경로 포함) |
| 3 | ✗ | ✗ | ✓ | **사지 않고 리뷰함** — 어뷰징 의심 계정, `verified=false`와 교차검증 |
| 4 | ✓ | ✓ | ✗ | 정상 전환, 리뷰만 미작성 |
| 5 | ✓ | ✗ | ✓ | 담아만 두고 리뷰 — 강한 이상 신호(체험/샘플이 아니라면 조사 대상) |
| 6 | ✗ | ✓ | ✓ | 즉시구매 후 리뷰 — 정상, 퍼널 단축 사례 |
| 7 | ✓ | ✓ | ✓ | 풀 퍼널 완주 — 이상적 고객 여정, LTV 세그먼트 |

여기서 파생되는 지표들이 전부 **경로 비교**로 정의된다.

- **전환율(conversion)** = `|Cart 경로 ∩ Order 경로| / |Cart 경로|` — 상태 4·7 대 상태 1의 비
- **리뷰율(review rate)** = 상태 6·7 대 상태 2·4
- **리뷰 신뢰도** = 상태 3·5의 비중, 그리고 `Review.verified`가 실제 Order 경로 존재와 일치하는지 대조

아티클의 *"Which buyers have full carts but no orders?"* (`Buyer → Cart(itemCount > 0)` 있고 `Buyer → Order` 없음), *"Which products are most often added to carts but not purchased?"* 도 전부 상태 1의 변형이다.

```gql
-- 담아뒀지만 사지 않은 상품 (상품 관점 집계)
MATCH (b:Buyer)-[:has_cart]->(c:Shopping-Cart)-[:contains]->(p:Product)
WHERE NOT EXISTS {
  MATCH (b)-[:places]->(:Order)-[:includes]->(p)
}
RETURN p.sku, p.name, COUNT(DISTINCT b) AS abandonedBy
ORDER BY abandonedBy DESC
```

> **정리**: 선형 체인은 "무엇이 일어났는가"만 답한다. 대체 경로가 생기면 **"무엇이 일어나지 않았는가"** 를 의미 있게 물을 수 있고, 비즈니스에서 돈이 되는 질문은 대개 후자 쪽(이탈, 미전환, 어뷰징, 미작성)에 있다.

## 3. "루프"라는 표현의 엄밀성 — 사실 순환(cycle)이 아니다

아티클은 *"creates a cycle back to Product"*, *"forming a loop"* 라고 쓰지만, 그래프 이론 용어로 보면 **부정확한 표현**이다. 세 층위로 나눠 짚어야 한다.

1. **loop (자기 루프)**: 엄밀한 정의로 loop는 한 정점에서 자기 자신으로 가는 엣지(self-loop)다. 이 온톨로지에는 그런 엣지가 하나도 없다. 이 의미의 "루프"는 아니다.
2. **directed cycle (유향 순환)**: 방향을 지켜서 출발점으로 돌아오는 경로. 이 온톨로지의 모든 엣지는 `Buyer → {Order, Cart, Review} → Product` 로 **한 방향으로만** 흐른다. Product에서 Buyer로 되돌아오는 엣지가 없으므로 **유향 순환은 존재하지 않는다**. 이 그래프는 위상정렬이 가능한 **DAG(유향 비순환 그래프)** 다.
3. **undirected cycle (무방향 순환) / 닫힌 경로**: 엣지 방향을 무시하면 `Buyer → Order → Product ← Review ← Buyer` 처럼 시작점으로 돌아오는 닫힌 경로가 생긴다. 아티클이 말하는 "loop"는 정확히 이것이다.

더 정확한 이름을 붙이자면 이 패턴은 **다이아몬드(diamond) 패턴** 또는 **다중 경로(multi-path) 패턴**이다. 위상적으로 표현하면 Buyer가 source, Product가 sink인 **s–t 다중 경로**이며, 무방향으로 변환했을 때 비로소 사이클이 된다.

용어를 왜 굳이 따지는가 — 실무적으로 결과가 다르기 때문이다.

- **진짜 유향 순환**이라면 재귀 질의(가변 길이 traversal `[:r*]`)에서 무한 순회 위험이 있어 방문 노드 추적·depth 제한이 필요하다. 이 그래프는 DAG이므로 그런 위험이 없다.
- **DAG의 다중 경로**는 순회를 멈추지 못하는 문제가 아니라 **경로가 여러 개라 결과 행이 곱해지는 문제(다이아몬드 fan-out)** 를 만든다. 대응 수단이 완전히 다르다 (아래 4절).
- "피드백 루프"는 **의미론적(비즈니스) 은유**다 — 구매자가 상품을 소비하고, 리뷰를 남기고, 그 리뷰가 다른 구매자의 구매에 영향을 준다. 이 되먹임은 **인스턴스 그래프에서 서로 다른 Buyer를 거쳐** 닫히는 것이지, **스키마 그래프의 엣지 방향으로** 닫히는 게 아니다. 스키마 수준에서 이 "loop"의 정체는 어디까지나 **동일 끝점을 잇는 대체 경로**다.

> 시험/면접에서 안전한 문장: *"방향을 지키면 Buyer→Product 한 방향뿐이라 유향 순환은 없고, 방향을 무시하면 Buyer와 Product를 잇는 서로 다른 경로들이 닫힌 경로를 만든다. 흔히 '피드백 루프'라 부르는 건 이 무방향 닫힌 경로이며, 질의 표현력 관점의 핵심은 '순환'이 아니라 '대체 경로'다."*

## 4. 경로가 늘어날 때 치르는 비용

대체 경로는 공짜가 아니다. 4개, 5개로 늘리기 전에 아래 대가를 인지해야 한다.

### 4-1. 모델 복잡도

- 엔티티 5개 / 관계 6개까지는 사람이 머리에 들고 다닐 수 있지만, 경로가 늘면 **"이 질문은 어느 경로로 답해야 하는가"** 자체가 모호해진다. Product 매출을 Order로 세는가, Cart subtotal로 세는가?
- **의미 중복(semantic overlap)** 위험: `Order.total`과 `Cart.subtotal`처럼 비슷한데 미묘하게 다른 값이 여러 경로에 흩어진다. 어느 것이 진실의 원천(source of truth)인지 문서화되지 않으면 지표가 갈라진다.
- 카디널리티 실수의 파급이 커진다. `has_cart`를 one-to-one이 아니라 one-to-many로 잘못 두면 이탈 지표가 통째로 틀어진다.

### 4-2. 질의 계획 폭발 (query plan explosion)

- 조인 순서 후보가 경로/관계 수에 따라 급격히 늘어난다(옵티마이저의 조인 순서 탐색 공간은 관계 수에 대해 초지수적으로 커진다). 다중 경로 + `NOT EXISTS`가 섞이면 옵티마이저가 잘못된 순서를 고를 확률이 올라간다.
- 부정 질의(anti-join)는 특히 취약하다. 선택도(selectivity) 추정이 어긋나면 nested-loop anti-join이 수억 행을 돌게 된다.
- 온톨로지 질의가 여러 소스 시스템(트랜잭션 DB / 검색엔진 / 분석 웨어하우스)으로 페더레이션되면 경로마다 **다른 물리 저장소**를 때리게 되어, 원격 조인 비용이 경로 수만큼 곱해진다.

### 4-3. 중복 행 (fan-out / 다이아몬드 문제)

가장 자주 실수하는 지점이다. 한 구매자가 같은 상품을 **주문 3건**에서 샀고 **리뷰 2건**을 썼다면, 두 경로를 순진하게 조인한 순간 (구매자, 상품) 쌍 하나가 **3 × 2 = 6행**으로 부풀어 오른다.

```gql
-- 위험: SUM(o.total)이 리뷰 개수만큼 뻥튀기된다
MATCH (b:Buyer)-[:places]->(o:Order)-[:includes]->(p:Product),
      (b)-[:writes]->(r:Review)-[:reviews]->(p)
RETURN b.buyerId, SUM(o.total)   -- 과대집계!
```

집계 지표(매출, 전환율)를 이런 다중 경로 조인 위에서 계산하면 **조용히 틀린 숫자**가 나온다. 에러가 안 나기 때문에 더 위험하다.

### 4-4. 완화 방법

| 문제 | 대응 |
|---|---|
| fan-out 중복 행 | 존재 여부만 필요하면 조인 대신 **semi-join/anti-join** (`EXISTS` / `NOT EXISTS`)을 써서 행을 늘리지 않는다 |
| 과대집계 | 경로별로 **먼저 집계한 뒤 조인**(pre-aggregate then join). 또는 `COUNT(DISTINCT o.orderId)` 처럼 식별자 기준 중복 제거 |
| 반복되는 다중 경로 판정 | 자주 쓰는 조합을 **파생 속성으로 물질화**. `Review.verified` 불리언이 정확히 이 사례 — "Order 경로 존재 여부"를 미리 계산해 박아둔 것이라 매번 anti-join을 돌 필요가 없다 |
| 재계산 비용 | `itemCount`, `subtotal` 같은 **비정규화 요약 속성**으로 경로 순회를 절약 (저장공간·정합성과의 교환) |
| 질의 계획 불안정 | 경로 시작점을 선택도 높은 쪽으로 고정, 식별자(`buyerId`, `sku`)에 인덱스, 가변 길이 traversal은 depth 상한 지정 |
| 모델 모호성 | 관계마다 **카디널리티와 의미를 명시**하고, 지표별 "정본 경로(canonical path)"를 문서에 못박는다 |
| 경로 남발 | 새 경로를 추가하기 전에 *"이 경로가 기존 경로와의 조합으로 어떤 새 질문을 여는가"* 를 먼저 적어본다. 새 질문이 없으면 그 경로는 관계가 아니라 그냥 속성이어도 된다 |

## 5. 한 줄 요약

선형 체인은 경로가 하나뿐이라 "무엇이 일어났는가"만 답한다. 같은 끝점을 잇는 대체 경로가 생기면 경로별 존재/부재의 조합이 2ⁿ 가지 상태를 만들고, 그 중 **"한쪽 경로는 있는데 다른 쪽은 없는"** 칸들이 이탈·미리뷰·어뷰징 같은 실전 질문에 정확히 대응한다. 다만 이 '루프'는 유향 순환이 아니라 무방향으로 봤을 때의 닫힌 경로이며, 대가로 fan-out 중복 행과 질의 계획 복잡도를 감수하고 semi-join·사전집계·파생 속성으로 이를 눌러야 한다.

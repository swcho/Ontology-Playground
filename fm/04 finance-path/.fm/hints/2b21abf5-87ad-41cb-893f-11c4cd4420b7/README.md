# "온톨로지는 데이터베이스가 아니라 스키마"

## 한 줄 요약

온톨로지는 **데이터의 모양(shape)** — 어떤 엔티티가 있고, 어떤 프로퍼티를 가지며, 무엇과 연결되는지 — 를 선언하는 **정의문서**다. 실제 레코드 값은 온톨로지 안으로 들어오지 않고 소스 시스템에 그대로 남는다. 그래서 `ssn` 같은 민감 필드는 온톨로지에 "이 프로퍼티가 존재한다"는 사실만 기술되고, 값 자체는 여전히 코어뱅킹 시스템에 있다.

학습 경로 원문의 표현:

> **Sensitive data note:** Properties like `ssn` appear in the ontology as metadata — they describe what data *exists*, not the actual values. The ontology is a schema, not a database.

---

## 1. 내포(intension) vs 외연(extension)

논리학·데이터 모델링에서 오래된 구분이 그대로 적용된다.

| | 내포 (intension) = 스키마 | 외연 (extension) = 인스턴스 |
|---|---|---|
| 무엇인가 | 개념의 정의, 조건 | 그 정의를 만족하는 실제 개체들의 집합 |
| 은행 예시 | "Customer는 `customerId`(식별자), `name`, `ssn`, `creditScore`(integer 300–850), `riskProfile`을 가진다" | `C-10293 / 김하나 / 123-45-6789 / 742 / medium` 이라는 한 줄 |
| 어디 사는가 | 온톨로지 계층 | 소스 시스템 (코어뱅킹 DB, 결제 처리사, 신용평가사, 증권사) |
| 크기 | 수십~수백 개 정의 | 수억 행 |
| 변경 성격 | 모델 변경(리뷰·승인 대상) | 데이터 변경(적재·갱신) |

온톨로지는 왼쪽 열만 담는다. Customer 엔티티를 정의했다는 것은 "고객이라는 개념은 이런 모양이다"라고 말한 것이고, 고객이 300만 명 있다는 사실이나 그들의 SSN을 온톨로지가 소유한 것은 아니다.

Account를 정의했다는 것도 마찬가지다. `balance`는 decimal(USD)라고 선언되어 있지만, 특정 계좌의 잔액 $4,182.30은 온톨로지가 아니라 원장 시스템의 값이다.

## 2. 아키텍처: 소스 시스템 위에 얹히는 계층

```
┌──────────────────────────────────────────────────────────┐
│  질의 / 애플리케이션 / 컴플라이언스 리포트                │
│  "고위험 고객이 보유한 계좌의 거래 중 대출 10만$ 초과"     │
└───────────────────────────┬──────────────────────────────┘
                            │ 온톨로지 용어로 질의
┌───────────────────────────▼──────────────────────────────┐
│  온톨로지 계층 (= 스키마, 값 없음)                        │
│   • 엔티티: Customer, Account, Transaction, Loan, ...     │
│   • 프로퍼티: customerId(id), ssn, creditScore:int, ...   │
│   • 관계: owns, has_transaction, has_loan, funds, ...     │
│   • 매핑: Customer.ssn  →  CORE_CUST.SSN_ENC             │
│           Account.balance → LEDGER.ACCT.BAL_USD          │
└───────────────────────────┬──────────────────────────────┘
                            │ 소스 질의로 번역(push-down)
┌───────────────────────────▼──────────────────────────────┐
│  소스 시스템 (= 실제 값 보관소)                           │
│  코어뱅킹 DB │ 결제 처리사 │ 신용평가사 │ 증권 플랫폼      │
└──────────────────────────────────────────────────────────┘
```

온톨로지 계층이 실제로 들고 있는 것은 세 가지뿐이다.

1. **엔티티/프로퍼티/관계의 정의** — 이름, 타입, 단위, 식별자 여부, 카디널리티
2. **소스 매핑** — 각 프로퍼티가 어느 시스템의 어느 컬럼에서 오는지
3. **의미 규칙** — `interestRate`는 %, `term`은 integer(months), `timestamp`는 datetime 등

값은 없다. 값은 질의 시점에 소스에서 읽힌다.

## 3. 질의 시점에 벌어지는 일: 온톨로지 → 소스 질의로 번역

경로 문서의 컴플라이언스 질문을 보자.

> "Show all transactions from accounts owned by high-risk customers with active loans exceeding $100K"

온톨로지 관점에서는 그래프 순회다.

```
Transaction → Account → Customer(riskProfile='high') → Loan(principal > 100000)
```

```gql
MATCH (c:Customer)-[:holds]->(inv:Investment),
      (c)-[:has_loan]->(loan:Loan)
WITH c, SUM(inv.currentValue) AS portfolio, SUM(loan.principal) AS debt
WHERE portfolio > debt
RETURN c.name, portfolio, debt
```

이 질의는 "온톨로지 DB"를 뒤지는 것이 아니다. 실행 엔진이 하는 일은:

1. `Customer`, `Loan`, `owns`, `has_loan` 같은 온톨로지 개념을 매핑 정보로 해석
2. 각 개념을 실제 테이블/API 호출로 치환 (`Customer` → `CORE_CUST`, `has_loan` → `LOAN.CUST_ID` 조인)
3. 관계 순회를 조인 또는 페더레이션된 다중 시스템 호출로 변환
4. 소스에서 값을 읽어 결과를 조립

즉 온톨로지는 **번역 사전**이지 저장소가 아니다. `owns` 관계는 "Customer.customerId = Account.ownerCustomerId 로 이어진다"는 규칙일 뿐, 300만 개의 소유 엣지를 물리적으로 복제한 것이 아니다.

(구현체에 따라 성능을 위해 캐시나 materialized 인덱스를 두기도 한다. 하지만 그것은 **성능 최적화의 산물**이고, 진실의 원천(system of record)은 여전히 소스다. 이 둘을 혼동하면 "온톨로지가 데이터를 갖고 있다"는 오해가 생긴다.)

## 4. 이 구분이 실무에서 만드는 결과

### 4.1 민감 데이터 거버넌스 — 선언과 접근권한의 분리

`ssn`을 온톨로지에 넣는 행위는 **SSN을 복사하는 것이 아니다.** 두 가지가 완전히 분리된다.

| 층 | 담당 | SSN에 대해 하는 일 |
|---|---|---|
| 온톨로지 | 데이터 모델러 | "Customer는 ssn:string 프로퍼티를 가진다"고 선언. 분류 태그(PII), 마스킹 정책, 목적 제한을 메타데이터로 붙임 |
| 소스 시스템 | DBA / 보안팀 | 실제 값 보관, 암호화, 컬럼 수준 접근제어, 감사 로그 |

실무적 효과:

- **온톨로지 열람 권한 ≠ 데이터 열람 권한.** 개발자가 온톨로지를 읽고 "SSN이라는 필드가 존재하며 신원 확인에 쓰인다"는 것을 알 수 있지만, 그것만으로 어떤 고객의 SSN 값도 볼 수 없다. 값 접근은 소스 시스템(및 그 위의 정책 엔진)이 통제한다.
- **모델링 리뷰를 안전하게 할 수 있다.** 온톨로지 정의는 실데이터가 아니므로, 위키에 붙이고 PR에서 토론하고 외부 컨설턴트와 화면 공유해도 개인정보 유출이 아니다. 반대로 실제 레코드 샘플을 공유하는 순간 그것은 유출이다.
- **데이터 카탈로그/영향 분석이 가능해진다.** "PII로 태깅된 프로퍼티가 어느 리포트에 흘러가는가"를 스키마만 훑어 계산할 수 있다. 값을 읽지 않고도 규제 대응(GDPR 처리목록, 데이터 매핑 문서)을 만든다.
- **최소권한이 자연스럽게 구현된다.** 대부분의 분석 질의는 `riskProfile`, `creditScore`, `balance`만 필요하다. `ssn`은 존재만 선언된 채 실제로는 극소수 역할에게만 해석(resolve)된다.

### 4.2 스키마 변경과 데이터 마이그레이션의 분리

온톨로지가 값을 안 들고 있다는 사실이 변경 비용 구조를 바꾼다.

- `Customer`에 `riskProfile`을 추가한다 → 온톨로지 정의 + 소스 컬럼 매핑 추가. **수억 행을 다시 쓰는 작업이 아니다.**
- 관계 하나를 새로 만든다 (`Account -funds-> Loan`) → 조인 규칙 선언. 엣지 테이블 벌크 로딩이 아니다.
- 프로퍼티 이름을 `apr`로 정리한다 → 온톨로지 라벨 변경, 소스 컬럼은 `ANN_PCT_RATE`로 그대로. 소스를 건드리지 않고 의미를 정리할 수 있다.
- 반대로 소스 스키마가 교체되어도(코어뱅킹 리플레이스) 온톨로지 정의는 유지하고 **매핑만 갈아끼운다.** 상위 질의·리포트·앱은 그대로 동작한다.

이 때문에 "모델 변경"과 "데이터 마이그레이션"은 별개의 릴리스 트랙이 된다. 전자는 리뷰가 필요한 논리적 변경, 후자는 운영 작업이다. 물론 완전히 무료는 아니다 — 기존 질의가 깨지는 breaking change(식별자 변경, 타입 변경, 관계 카디널리티 변경)는 여전히 신중해야 하고, 소스에 대응 값이 없는 프로퍼티를 선언하면 스키마는 통과하지만 질의는 빈 결과를 낸다.

### 4.3 온톨로지를 버전 관리·리뷰 가능한 산출물로 다룰 수 있는 이유

온톨로지가 값 없는 정의이기 때문에 가지는 성질:

- **작다** — 이 은행 모델 전체가 엔티티 5개, 관계 6개다. 텍스트 몇 KB.
- **결정적이다** — 같은 정의는 항상 같은 의미. 시점에 따라 달라지는 잔액 같은 요소가 없다.
- **선언적이다** — 순서·절차가 아니라 상태 기술이므로 diff가 의미를 갖는다.

그래서 온톨로지는 코드처럼 취급된다.

- Git에 넣고 diff를 본다 (`finance-step-1` → `step-2`에서 Transaction 엔티티와 `has_transaction` 관계가 추가됨 — 학습 경로의 `diff="official/finance-step-1"` 임베드가 정확히 이 발상이다)
- PR로 리뷰한다: "`merchant`를 프로퍼티로 둘지 Merchant 엔티티로 승격할지", "`timestamp`가 date면 부정거래 탐지가 안 된다"
- 태그를 붙여 버전을 릴리스하고, 롤백하고, 환경 간(dev/staging/prod) 승격한다
- CI에서 검증한다: 모든 엔티티에 식별자가 있는가, 고아 엔티티가 없는가, 단위가 선언되었는가

실데이터가 섞여 있다면 이 중 어느 것도 깔끔하게 되지 않는다. 수억 행을 Git에 넣을 수도, 개인정보가 든 스냅샷을 PR에 올릴 수도 없다.

## 5. 흔한 오해 바로잡기

### 오해 1: "온톨로지를 만들면 데이터가 복제된다"

아니다. 온톨로지 구축은 ETL로 데이터를 새 저장소에 밀어넣는 작업이 **아니고**, 소스 컬럼에 의미를 붙이는 작업이다. 실제로 늘어나는 저장 용량은 정의와 매핑 메타데이터뿐이다.

이 오해가 위험한 이유: 복제라고 믿으면 "그럼 SSN을 온톨로지에 넣으면 PII가 한 곳 더 늘어나는 거네, 넣지 말자"는 잘못된 결론에 도달한다. 그러면 모델에서 신원 확인 개념이 사라지고, 아무도 그 데이터가 존재한다는 사실을 모델 차원에서 알 수 없게 된다. 옳은 결론은 **"존재는 선언하고 값 접근은 소스 권한으로 통제한다"** 다.

### 오해 2: "온톨로지 = 그래프 데이터베이스"

관계를 그리고 GQL 같은 문법으로 순회한다는 점이 비슷해 보이지만 층이 다르다.

| | 온톨로지 | 그래프 DB |
|---|---|---|
| 정체 | 의미 계층 / 스키마 | 저장 엔진 |
| 담는 것 | 타입·관계 정의, 소스 매핑 | 실제 노드·엣지 레코드 |
| 데이터 위치 | 소스에 잔류 | 자기 안에 저장 |
| 대체 관계 | 그래프 DB 없이도 성립 (관계형 소스 위에 얹을 수 있음) | 온톨로지 없이도 성립 |

그래프 DB는 온톨로지를 구현하는 **하나의 선택지**일 뿐이다. 이 학습 경로의 은행 모델도 소스가 관계형 코어뱅킹 DB와 REST API 조합인 것이 현실적이며, 그래프 모양은 논리적 뷰다. "그래프처럼 질의된다"와 "그래프로 저장된다"는 다른 얘기다.

### 오해 3: "온톨로지에 프로퍼티가 있으면 그 값을 조회할 수 있다"

프로퍼티 선언은 **가능성**이고, 실제 조회 가능성은 (a) 소스에 값이 실제로 있는가, (b) 매핑이 되어 있는가, (c) 호출자가 그 소스에 권한이 있는가 세 조건에 달려 있다. `ssn`이 정의되어 있어도 일반 분석가 세션에서는 마스킹되거나 접근 거부된다.

### 오해 4: "스키마니까 그냥 문서 아닌가, 실행에 영향이 없다"

아니다. 온톨로지는 **실행되는 스키마**다. `creditScore`를 integer로 선언했기 때문에 질의 엔진이 `creditScore > 700` 범위 질의를 밀어넣을 수 있고, `timestamp`를 datetime으로 선언했기 때문에 분 단위 부정거래 패턴을 볼 수 있다. 타입·단위·카디널리티는 장식이 아니라 질의 능력의 계약이다.

## 6. 실제 사례: Palantir Foundry의 온톨로지 계층

Foundry 문서는 온톨로지를 플랫폼에 통합된 디지털 자산(dataset, virtual table, model) **위에 놓이는 의미 계층(semantic layer)** 으로 설명한다. 조직의 의미를 정의하는 방식은 "기존 데이터소스를 객체(object type)·프로퍼티·링크로 **매핑하는 것**"이며, 온톨로지는 이렇게 현실 세계의 대응물(설비, 제품, 고객 주문, 금융 거래 같은 개념)과 데이터를 연결한다. 매핑은 Ontology Manager(로우코드) 또는 TypeScript/Python SDK로 수행한다.

즉 상용 구현에서도 흐름은 같다 — 정의와 매핑이 온톨로지에, 값은 아래층 자산에. 다만 실제 제품은 성능을 위한 인덱싱/구체화 계층(object backend)을 함께 운영하므로, "값이 물리적으로 절대 어디에도 사본이 없다"는 뜻은 아니다. 핵심은 **의미의 정의와 값의 소유가 분리되어 있고, 접근 통제가 값을 가진 층에서 걸린다**는 점이다.

## 7. 기억할 문장

- 온톨로지는 **"무엇이 존재하는가"** 를 말하고, 데이터베이스는 **"그것이 무엇인가"** 를 말한다.
- 카드의 답을 다시 쓰면: 온톨로지는 데이터의 **모양과 구조**만 정의하고 레코드 값을 저장하지 않는다. 그래서 `ssn`은 소스에 남고 온톨로지에는 **존재만 기술**된다.
- 학습 경로의 마지막 정리 문장도 같은 말이다: *"Financial ontologies describe data shape — sensitive data stays in source systems."*
